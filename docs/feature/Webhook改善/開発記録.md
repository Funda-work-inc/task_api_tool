## 🎯 目的・背景

### なぜこの実装が必要だったか

Webhook受信履歴の視認性と利便性を向上させるため。現状では`/webhooks`ページでしか履歴を確認できず、手動でリロードする必要があり、表示される情報も最小限だった。

### 解決したい課題

1. **視認性の問題**: Webhook履歴が`/webhooks`ページでしか見られない
2. **リアルタイム性の欠如**: 手動でページをリロードしないと最新情報が見られない
3. **情報不足**: 表示される情報が最小限で、詳細が分かりにくい

### 期待される効果

- **技術的メリット**: リアルタイム更新により、開発時のデバッグ効率が向上
- **ビジネス的メリット**: Webhookイベントの監視が容易になり、問題の早期発見が可能
- **学習目標**: TDD、JavaScript fetch API、ポーリング、セッション管理の理解

```javascript
// Webhook履歴の自動更新（ポーリング）
function fetchWebhookLogs() {
  fetch('/api/webhook_logs')
    .then(response => response.json())
    .then(data => {
      const logsContainer = document.getElementById('webhook-logs-tbody');
      const emptyMessage = document.getElementById('webhook-empty-message');
      const logsTable = document.getElementById('webhook-logs-table');

      if (data.webhook_logs && data.webhook_logs.length > 0) {
        emptyMessage.style.display = 'none';
        logsTable.style.display = 'table';
        logsContainer.innerHTML = '';

        data.webhook_logs.slice(0, 5).forEach(log => {
          const row = document.createElement('tr');

          let eventBadgeClass = '';
          let eventLabel = '';
          if (log.event === 'created') {
            eventBadgeClass = 'badge-success';
            eventLabel = '✨ 作成';
          } else if (log.event === 'updated') {
            eventBadgeClass = 'badge-warning';
            eventLabel = '✏️ 更新';
          } else if (log.event === 'destroyed') {
            eventBadgeClass = 'badge-danger';
            eventLabel = '🗑️ 削除';
          }

          row.innerHTML = `
            <td><span class="badge ${eventBadgeClass}">${eventLabel}</span></td>
            <td>${log.task.id}</td>
            <td>${log.task.title}</td>
            <td><span class="badge badge-${log.task.priority}">${log.task.priority || 'N/A'}</span></td>
            <td>${log.task.due_date || 'N/A'}</td>
            <td>${formatTimestamp(log.timestamp)}</td>
          `;

          logsContainer.appendChild(row);
        });
      } else {
        emptyMessage.style.display = 'block';
        logsTable.style.display = 'none';
      }
    })
    .catch(error => {
      console.error('Webhook履歴の取得に失敗しました:', error);
    });
}

function formatTimestamp(timestamp) {
  const now = new Date();
  const past = new Date(timestamp);
  const diffMs = now - past;
  const diffSec = Math.floor(diffMs / 1000);
  const diffMin = Math.floor(diffSec / 60);
  const diffHour = Math.floor(diffMin / 60);

  if (diffSec < 60) {
    return `${diffSec}秒前`;
  } else if (diffMin < 60) {
    return `${diffMin}分前`;
  } else if (diffHour < 24) {
    return `${diffHour}時間前`;
  } else {
    return timestamp;
  }
}

fetchWebhookLogs();
setInterval(fetchWebhookLogs, 10000);
```

### 遭遇したエラー一覧

#### エラー1: OpenSSL暗号化エラー（テスト環境）

**エラーメッセージ:**

```
OpenSSL::Cipher::CipherError: couldn't set additional authenticated data
```

**発生状況:**
- テスト実行時に全テストで発生
- セッションにアクセスする処理で発生

**原因:**
- Sinatraの`enable :sessions`がデフォルトで暗号化セッションを使用
- テスト環境ではOpenSSL暗号化の設定が不足していた

**解決方法:**

テスト環境では暗号化なしのCookieセッションを使用するように修正。

```ruby
if ENV['RACK_ENV'] == 'test'
  use Rack::Session::Cookie, secret: 'test_secret'
else
  enable :sessions
end
```

**学び:**
- 環境ごとに設定を切り替える重要性
- テスト環境ではシンプルな設定で十分なケースがある
- セキュリティと開発効率のバランス

---

#### エラー2: Webhook URL port mismatch

**エラーメッセージ:**

```
❌ Webhook送信失敗: 接続できません（http://localhost:4567/webhook）
```

**発生状況:**
- task_learning_appでタスクを作成してもWebhookが届かない
- task_learning_appのログに「Webhook送信成功」と表示されない
- task_api_toolのログにWebhook受信の記録がない

**原因:**
- task_learning_appの`WebhookNotifier`クラスで、Webhook送信先URLが`http://localhost:4567/webhook`に設定されていた
- しかし、task_api_toolは**port 4568**で起動していた（port 4567は別のプロセスが使用中だった）
- ポート番号のミスマッチにより、Webhookが宛先不明で送信失敗

**解決方法:**

task_learning_appの`app/services/webhook_notifier.rb:8`を修正。

```ruby
# Before
WEBHOOK_URL = 'http://localhost:4567/webhook'

# After
WEBHOOK_URL = 'http://localhost:4568/webhook'
```

**学び:**
- マイクロサービス間の通信では、URL（特にポート番号）の一致が重要
- サーバー起動時に実際に使用しているポート番号を確認する習慣
- エラーログを確認することで、問題箇所を素早く特定できる

#### エラー3: OpenSSL暗号化エラー（開発環境）

**エラーメッセージ:**

```
OpenSSL::Cipher::CipherError at /
couldn't set additional authenticated data
file: encryptor.rb location: auth_data= line: 30
```

**発生状況:**
- ブラウザでhttp://localhost:4568にアクセスすると500 Internal Server Error
- サーバーログにOpenSSL暗号化エラーが表示
- シークレットウィンドウでも同じエラーが発生

**原因:**
- エラー1の解決で、テスト環境だけCookieセッションに変更したが、**開発環境では依然として暗号化セッション**を使用していた
- Ruby 2.6.10のOpenSSLバージョンとSinatraの暗号化セッション機能の互換性問題
- task_learning_app（Ruby 3.3.0）の暗号化Cookieがブラウザにセットされており、task_api_tool（Ruby 2.6.10）がそれを復号化しようとして失敗

**解決方法（試行1回目）:**

開発環境でもCookieセッションを使用するように修正。

```ruby
if ENV['RACK_ENV'] == 'test'
  use Rack::Session::Cookie, secret: 'test_secret'
else
  # 開発環境でもCookieセッション
  use Rack::Session::Cookie, secret: 'development_secret'
end
```

**結果**: エラーは解消されたが、後に**さらに深刻な問題**が発覚（エラー4参照）

**学び:**
- 異なるRubyバージョン間でセッション暗号化方式が異なる場合がある
- 複数アプリケーションが同じドメイン（localhost）を使用する場合、Cookie衝突に注意
- エラー解消は一時的な対症療法の可能性があり、根本原因の特定が重要

#### エラー4: セッション共有問題（VIEW上にWebhook履歴が表示されない）

**症状:**

- サーバーログには「🔔 Webhook受信！」と表示され、Webhook自体は受信できている
- しかし、トップページ（http://localhost:4568/）の「🔔 Webhook受信履歴」セクションに何も表示されない
- GET /api/webhook_logsのレスポンスが`{"webhook_logs":[]}`（空配列）
- /webhooksページにも履歴が表示されない
- シークレットウィンドウでも同じ問題が発生

**発生状況:**

```
# サーバーログ
==================================================
🔔 Webhook受信！
イベント: created
タスクID: 16
タスク名: クビーーーー
発生時刻: 2025-12-21T06:34:52Z
==================================================
[stderr] ::1 - - [21/Dec/2025:15:34:52 +0900] "POST /webhook HTTP/1.1" 200 45 0.0014
[stderr] ::1 - - [21/Dec/2025:15:34:52 +0900] "GET /api/webhook_logs HTTP/1.1" 200 19 0.0014
                                                                                      ^^
                                                                            わずか19 bytes（空のJSON）
```

**原因分析:**

最初は「ブラウザのCookieが古いのでは？」と考えたが、シークレットウィンドウでも同じ症状が出たため、**根本的な設計問題**だと判明。

**根本原因:**

POST /webhookとGET /api/webhook_logsが**別々のセッション**を使用していた。

1. **POST /webhook**（task_learning_appからのサーバー間通信）
   - HTTPリクエストヘッダーに**Cookieなし**
   - 新しいセッションが自動的に作成される
   - `session[:webhook_logs]`にデータを保存
   - しかし、このセッションはリクエスト終了後に破棄される（Cookieが保存されないため）

2. **GET /api/webhook_logs**（ブラウザからのリクエスト）
   - HTTPリクエストヘッダーに**Cookieあり**
   - ブラウザが保持しているセッションCookieを使用
   - `session[:webhook_logs]`を読み取るが、**別のセッション**なので空配列

**図解:**

```
task_learning_app                   task_api_tool
     (Ruby 3.3.0)                    (Ruby 2.6.10)
         |                                 |
         | POST /webhook                   |
         | (Cookieなし)                    |
         |-------------------------------->|
         |                                 | セッションA作成
         |                                 | session[:webhook_logs] = [...]
         |                                 | ← セッションA破棄（Cookie保存なし）
         | 200 OK                          |
         |<--------------------------------|
         |                                 |
                                           |
ブラウザ                                   |
    |                                     |
    | GET /api/webhook_logs               |
    | (Cookie: セッションB)               |
    |------------------------------------>|
    |                                     | セッションB読み込み
    |                                     | session[:webhook_logs] → []（空）
    | {"webhook_logs": []}                |
    |<------------------------------------|
    |
```

**解決方法:**

セッション（Cookie）ではなく、**クラス変数（メモリ内）**でWebhook履歴を保存するように変更。

**app.rb:5〜21行目に追加:**

```ruby
# Webhook履歴をメモリ内に保存するクラス変数
class WebhookHistory
  @@logs = []

  def self.add(log)
    @@logs.unshift(log)
    @@logs = @@logs.first(10) # 最新10件まで保持
  end

  def self.all
    @@logs
  end

  def self.clear
    @@logs = []
  end
end
```

**app.rb:162〜167行目を修正（POST /webhook）:**

```ruby
# Before
session[:webhook_logs] ||= []
session[:webhook_logs].unshift({
  event: payload['event'],
  task: payload['task'],
  timestamp: payload['timestamp']
})
session[:webhook_logs] = session[:webhook_logs].first(10)

# After
WebhookHistory.add({
  event: payload['event'],
  task: payload['task'],
  timestamp: payload['timestamp']
})
```

**app.rb:192〜194行目を修正（GET /api/webhook_logs）:**

```ruby
# Before
webhook_logs = session[:webhook_logs] || []

# After
webhook_logs = WebhookHistory.all
```

**app.rb:187行目を修正（GET /webhooks）:**

```ruby
# Before
@webhook_logs = session[:webhook_logs] || []

# After
@webhook_logs = WebhookHistory.all
```

**セッション設定も最終的に修正（app.rb:23〜29）:**

```ruby
# 最終版
if ENV['RACK_ENV'] == 'production'
  # 本番環境では暗号化セッション
  enable :sessions
else
  # 開発・テスト環境ではCookieセッション（暗号化なし）
  use Rack::Session::Cookie, secret: 'development_secret_key_change_in_production'
end
```

**学び:**

1. **セッションの特性を理解する**
   - セッションはCookieベースで、ブラウザとサーバー間の通信でのみ機能
   - サーバー間通信（Webhook等）ではCookieが送信されないため、セッションは共有されない

2. **データ保存先の選択**
   - ブラウザ間で共有したい→セッション
   - 全リクエストで共有したい（サーバー間通信含む）→クラス変数、データベース、Redis等
   - 永続化が必要→データベース
   - 一時的なデータ→クラス変数（メモリ）

3. **デバッグ手法**
   - ログを詳細に確認する（レスポンスサイズ、ステータスコード）
   - 「動いているように見えるが実際は動いていない」ケースに注意
   - セッションIDをログに出力して、同じセッションかどうか確認する

4. **トレードオフの理解**
   - クラス変数はサーバー再起動で消える（永続化なし）
   - 今回は開発・学習目的なので許容範囲
   - 本番環境ではデータベースやRedisを検討すべき

**この問題の発見過程:**

1. 「Webhookが届かない」→ port mismatch発覚（エラー2）
2. port修正後「OpenSSLエラー」→ セッション設定修正（エラー3）
3. セッション修正後「ログには出るがVIEWに表示されない」→ **真の原因発覚**（エラー4）

**結論:**

表面的なエラーメッセージだけでなく、**データの流れ全体**を理解することが重要。特に、セッション、Cookie、サーバー間通信の仕組みを正しく理解していないと、根本原因にたどり着けない。

## 🎓 学習記録

### 新しく学んだ概念・技術

#### 概念1: JavaScriptポーリング

- **説明**: 一定間隔でサーバーにリクエストを送信して最新情報を取得する手法
- **使用場面**: リアルタイム性が求められるが、WebSocketほど複雑にしたくない場合
- **注意点**: ポーリング間隔が短すぎるとサーバー負荷が高くなる
- **コード例**:

```javascript
function fetchData() {
  fetch('/api/data')
    .then(response => response.json())
    .then(data => {
      // データを処理
    });
}

// 10秒ごとに実行
setInterval(fetchData, 10000);
```

#### 概念2: 環境変数による条件分岐

- **説明**: `ENV['RACK_ENV']`でテスト/開発/本番環境を判定して設定を切り替える
- **使用場面**: 環境ごとに異なる設定が必要な場合
- **注意点**: 全ての環境で動作確認すること
- **コード例**:

```ruby
if ENV['RACK_ENV'] == 'test'
  # テスト環境の設定
elsif ENV['RACK_ENV'] == 'production'
  # 本番環境の設定
else
  # 開発環境の設定
end
```

### 理解できたこと

1. **TDDの効果**:
   - テストを先に書くことで、実装の方向性が明確になる
   - エラーが発生した時、テストがあることで素早く原因を特定できる

2. **セッション管理の環境差分**:
   - 本番環境とテスト環境でセッションの扱いが異なることを理解
   - セキュリティと開発効率のバランスを考慮する必要性

3. **JavaScriptのfetch API**:
   - 非同期通信の実装方法
   - Promise, then, catchの使い方
